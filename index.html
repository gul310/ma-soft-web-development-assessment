Q1: Logic & Event Handling Architecture

1. How Application State Is Maintained

State is encapsulated in ItemStore (an ES6 singleton). The store manages an in-memory array of item objects, serializes mutations to localStorage through StorageService, and publishes change events over EventBus to trigger re-renders.

2. How Items Are Added

Upon form submission, inputs are validated and sanitized via cleanInputString(). If valid, itemStore.addItem() generates a timestamped identifier, sets completed: false, prepends the object to the state array, and saves to storage.

3. How Items Are Edited

Clicking the edit button triggers enableInlineEdit(). The text nodes are swapped for validated input fields in place. When saved, the controller validates the modified values and calls itemStore.updateItem(id, updates), updating state and DOM in-memory.

4. How Items Are Deleted & Restored

Clicking delete identifies the item by dataset.id, splices it from state, and pushes a record onto an internal undo history stack. A non-blocking toast notification is dispatched with an interactive Undo action that restores the deleted item to its exact previous index.

5. How DOM Rendering Works Efficiently

Dynamic rendering utilizes DocumentFragment. All <li> item nodes are built off-screen and appended into the memory fragment. The fragment is then attached to #q1-items-container in one single reflow rather than $N$ separate repaints.

6. Why Page Reload Is Unnecessary

Browser form submission defaults are intercepted via e.preventDefault(). State changes mutate the client data structure directly, and DOM nodes are patched without destroying the browser runtime context or dropping network connections.

7. How Event Delegation Works

Instead of binding listeners to every dynamically generated button, a single event listener is attached to the static parent <ul id="q1-items-container">. Through native event bubbling, clicks bubble up to the container where e.target.closest('[data-action]') inspects the action attribute.

8. Why Event Delegation Is Useful for Dynamic Content

1) Zero Memory Leaks: Adding or removing 1,000 items creates zero new event listeners.
2) No Re-binding Overhead: Newly inserted items work automatically without requiring manual addEventListener attachment after each render.

9. How Validation Works

Validation enforces: 1) Required title non-empty, 2) Whitespace-only rejection via .trim(), 3) Minimum length $\ge 3$ and maximum $\le 60$ characters, 4) Optional description maximum $\le 250$ characters, 5) Allowed priority enum check. Specific accessible error messages are displayed below invalid controls.

10. How User Feedback Is Generated

The application dispatches accessible toast notifications (Success, Warning, Info, Error) with ARIA live region announcements, updates live statistics counters in the header strip, and highlights invalid input borders in red with descriptive error text.

Q3: REST API & Failed Response Architecture

              
            

            

              
1. Asynchronous Handling with AbortController

              

                In modern web applications, rapid user typing can dispatch multiple overlapping HTTP requests. We wrap native fetch() inside an ApiService that instantiates an AbortController. If a new request is fired while a previous request is in-flight, controller.abort() cancels the stale promise immediately, saving client bandwidth and preventing race condition bugs.
              


              
2. Defense Against Failed API Responses

              

                fetch() only rejects promises on network dropouts, not on HTTP 4xx or 5xx status codes. We evaluate if (!response.ok) explicitly and throw typed errors (e.g. HTTP 404, HTTP 500).
              

              
    
                
  • HTTP 404/500: Caught and presented through a non-blocking error container with a dedicated Retry action.
    • 
                
  • Network Offline: Detected via navigator.onLine before request execution.
    • 
                
  • Timeout Protection: 10-second auto-abort threshold ensures the UI never hangs indefinitely.
    • 
              


              
3. Performance Caching

              

                Successful API payloads are stored in an in-memory Map() cache. Subsequent tab switches or local searches read directly from cache without hitting the network, while the "Reload API Data" button allows explicit cache-bypassing.

Comprehensive Technical Justifications (6 Best Practices)

          
          

            

              Practice 1
              Secure User-Input Handling & Sanitization
            

            

              Why it matters: User input is inherently untrusted. Malicious inputs can lead to HTML injection, SQL/NoSQL injection (if forwarded), or layout distortion. In this project, all inputs undergo automatic whitespace normalization (via cleanInputString()), URL protocol verification (stripping javascript: and data: protocols), and schema validation before any state updates.
            

          


          

            

              Practice 2
              Strict Cross-Site Scripting (XSS) Prevention
            

            

              Why it matters: Using innerHTML to render user-generated content allows attackers to inject malicious <script> or event-handler tags (e.g. <img onerror>) to hijack session tokens or deface pages. This application strictly utilizes document.createElement() and element.textContent for all dynamic rendering, neutralizing HTML characters inherently.
            

          


          

            

              Practice 3
              Multi-Tier Client-Side Form Validation
            

            

              Why it matters: Comprehensive validation prevents bad data from reaching application stores or backend servers, reducing load and improving UX. We implement real-time keystroke hints, blur-event validation, RFC 5322 email regex, international phone formatting, entropy password evaluation, and safe submit button locking.
            

          


          

            

              Practice 4
              Optimized DOM Operations & Event Delegation
            

            

              Why it matters: Attaching hundreds of event listeners consumes memory and causes listener leaks when elements are removed. Through Event Delegation, a single listener on parent lists (Q1, Q3, Q4) handles all child actions via event.target.closest(). Furthermore, all list updates build an off-screen DocumentFragment before committing to the DOM in a single atomic reflow.
            

          


          

            

              Practice 5
              Resource & Asset Optimization
            

            

              Why it matters: Heavy external assets cause high Largest Contentful Paint (LCP) and Cumulative Layout Shift (CLS). We use inline SVG icons and native system font stacks with clean Google Font fallbacks, CSS variables for instantaneous zero-re-render dark/light theming, and CSS containment (contain: content).
            

          


          

            

              Practice 6
              Reduction of Unnecessary Network Requests
            

            

              Why it matters: Unchecked search inputs fire an HTTP request per keystroke, overloading servers and triggering race conditions. We implement a 300ms Debounce utility, AbortController to cancel stale in-flight requests, and an in-memory caching layer that avoids re-fetching identical API payloads.

📖 Version Control & Accidental Loss Prevention

            

            

              

                
How Version Control Prevents Accidental Loss & Overwriting

                

                  1. Immutable Commit History: Every commit in Git is cryptographically hashed using SHA-1/SHA-256. Once committed, a file's state cannot be lost or secretly modified without altering history. Even if uncommitted working tree edits are discarded, committed states remain recoverable via git reflog.
                

              


              

                
2. Feature Branch Isolation:

                

                  By developing discrete features on dedicated branches (e.g. feature/q2-form-validation), developers can experiment, refactor, and test without affecting the stable main branch. Multiple engineers can work simultaneously on the same codebase without overwriting each other's work.
                

              


              

                
3. Non-Destructive Conflict Resolution:

                

                  When two developers modify the same lines of code, Git prevents silent overwrites by flagging a Merge Conflict. The merge stops, marking conflict boundaries with <<<<<<< HEAD and >>>>>>> feature, forcing developers to consciously reconcile differences before completing the merge.
